## 1. 文書の役割と正本

| 文書 | 正本の内容 | 禁止事項 |
|---|---|---|
| `docs/specs/**` | 外部仕様・規範・エラー・境界・互換性 | テストケース、実行手順、結果の混在 |
| `docs/design/**` | 仕様を実現するアーキテクチャ・責務・所有権・データフロー・失敗時処理 | 規範仕様の二重定義 |
| `docs/testing/**` | テスト条件・Oracle・入力・操作・期待結果・閾値 | 製品規範の重複正本化 |
| Issue ADC | 今回の作業義務・判断・対象ファイル・禁止変更・完了条件 | 大量の既存仕様/コードの全文転載 |
| PR/CI Evidence | 実行結果と検証証拠 | 実行未確認の成功宣言 |

製品仕様書での `Verification strategy` 必須章を撤廃し、検証内容の正本はテスト仕様とVerification Planへ移す。

## 2. 文書種類

製品/機能、UI・画面遷移、Web/SDK API、CLI、設定、ファイル形式・DSL、データモデル、状態機械、通信/イベント、プラグイン、認可、移行、更新、デバイス、リアルタイム等。共通品質規則と種類別章を組み合わせ、巨大な単一Markdownを強制しない。

## 3. 仕様から設計への確定順序

- 外部動作を変更する場合、変更後仕様の決定を先に確定し、それを満たす設計の決定を確定する。
- 設計変更のみの場合は仕様不変を証拠化。文書整理では内容の規範意味を変更しない。
- すべてのIssueが3種類の文書を変更する必要はない。`artifact_impact`に `create|update|unchanged(reason)|not_applicable(reason)` を明示。

## 4. 仕様・設計・テスト間の参照

規範は安定したREQ-ID、設計判断はDES-ID、検証条件はTST-ID/Oracle-IDを持ち、リンク検証と `REQ → DESIGN → ORACLE/TEST → EVIDENCE` の到達性を確認。テストが不要なREQは技術的理由と適切な代替Acceptanceを明示する。

## 5. Markdownのソース整形

- 原本 `.md` のH1は無番号、H2以降を自動採番。目次と見出しマップも原本に埋め込み更新。
- コードフェンスと生テキストは採番対象外。手動見出しアンカー・GitHub slug重複、番号変更時のMarkdown相対リンクも整合。
- `docs format --write` は冪等、`docs format --check` は非破壊で不一致を検出。ハッシュ固定されたADCコメントは整形対象外。
- 生成ディストリビューションはビルダーでのみ再生成する。
